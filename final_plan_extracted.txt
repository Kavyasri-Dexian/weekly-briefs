2. Data Source Resolution — Price + Arrivals Together
Confirmed data source: https://agmarknet.gov.in/home — Agmarknet's own site, as specified. This is the primary and mandated source for this plan.
Verified directly (not assumed): a plain request to agmarknet.gov.in/home returns HTTP 403 — the site actively blocks simple automated fetches. This is consistent with two existing open-source Agmarknet scrapers (GitHub: jha-vineet69/AgriMarket, iancovert/Agmarknet), both of which had to use full browser automation (Selenium) rather than a plain HTTP request to get through. The working path is Selenium + BeautifulSoup — both open source — driving a real browser session against Agmarknet's 'Daily Price and Arrival Report' page, which is confirmed by those two prior projects to carry State, District, Market, Variety, Group, Arrivals (Tonnes), Min/Max/Modal Price, and Reported Date — the full field set this plan needs, including tonnage.
This is real, proven-feasible work, but it is slower to stand up than a REST API call — Day 1 budgets real time for it rather than treating it as a quick task. Two fallbacks exist ONLY as a time-risk mitigation if Selenium scraping cannot be reliably stood up within Day 1's budget — they are not substitutes for the specified source, they are what keeps the 4-day plan from collapsing if agmarknet.gov.in's scraping proves harder to stabilize than expected (e.g. aggressive bot-detection escalation, CAPTCHA, session/cookie handling):

3. Architecture — Unchanged Principle
The accuracy guarantee still comes from one rule, carried through every version of this plan: no model, open-source or otherwise, is ever the source of a number. Compute every statistic in code from the raw Agmarknet records, freeze it into a per-district fact sheet, and only then let a language model turn that fact sheet into readable prose. A deterministic checker verifies every number in the generated brief against the fact sheet before anything is allowed to publish.
Compute (Python/pandas) → Fact Sheet (JSON, all ~15-16 fields retained) → Narrate (Qwen3, open source) → Translate (IndicTrans2, open source) → Verify (numeric diff-checker + HHEM-2.1-Open grounding score, both open source) → Human review → Publish.

7. Step-by-Step Plan
Day 1 — Stand Up Agmarknet Access, Pull Real Records
Step 1.1 — Set up Selenium (open source) with a headless browser driver, and BeautifulSoup for parsing. Point it at agmarknet.gov.in/home, navigate to the Daily Price and Arrival Report section, and confirm a real page loads (not a 403) — a rendered browser session should get past the bot-detection that blocks plain requests.
Step 1.2 — Script the report filters (State = Madhya Pradesh, date range, ALL districts rather than one at a time if the report supports a state-wide pull) and the pagination the existing prior-art scrapers describe (the site loads 50 rows at a time with a 'Next' control). Start with ONE district as a smoke test before scaling the same script state-wide — validate correctness on a small slice before running it across ~50-55 districts.
Step 1.3 — Confirm the scraped rows include the full field set: State, District, Market, Commodity, Variety, Group, Arrivals (Tonnes), Min/Max/Modal Price, Reported Date. If arrivals-in-tonnes is present (expected, per Section 2), the primary source is working — proceed to Step 1.5.
Step 1.4 — Time-check: if stabilizing the scraper (session handling, pagination, rate limiting, any CAPTCHA) is clearly going to consume most of Day 1, switch to a fallback from Section 2's table (data.gov.in API first, since a working client already exists) rather than let it eat into Day 2. Log this decision explicitly if it happens.
Step 1.5 — Run the scraper across ALL Madhya Pradesh districts and log the complete raw field list — extend the pipeline's field mapping to capture everything the source actually returns, not just a subset. State-wide volume (240-340 markets) will take materially longer to scrape than a handful of districts — budget real time for this and consider running it as a long background job rather than a quick foreground script, with retry/resume logic so a mid-run failure doesn't force a full restart.
Step 1.6 — Pull a SECOND week of historical data (the prior 7-day window) for the same state-wide scope, needed for Day 2's week-on-week comparison — the report's date-range filter supports this directly.
End of Day 1 exit criteria: real records for ALL Madhya Pradesh districts, 2 consecutive weeks, from agmarknet.gov.in directly (or a logged, explicit fallback if Step 1.4 triggered), with market, commodity, variety, arrivals (tonnes), min/max/modal price, and reported date all present and confirmed live — not assumed. If full state-wide scraping cannot complete within Day 1, this is the sprint's most likely schedule risk — see Section 8.
Day 2 — Compute Everything, No Model Involved Yet
Step 2.1 — Build the per-market-per-day submission-status table: submitted-with-trade, submitted-no-transaction, or not-submitted, for every market against every day in the window (see Section 6 — this is what makes 'if no transaction, still submit' true rather than aspirational).
Step 2.2 — Compute arrivals totals by commodity (the wheat/rice/maize tonnage requirement) and separately flag horticulture-category commodities (tomato, onion, potato etc.) using whatever commodity-group/type field the locked-in source provides.
Step 2.3 — Compute the most-traded commodity ranking by arrival volume (falling back to price-quote count only if Day 1 ultimately could not secure a tonnage-bearing source — flag this explicitly if it happens, don't silently substitute).
Step 2.4 — Compute percent price change per commodity between the two pulled weeks; rank top 3 gainers and top 3 decliners.
Step 2.5 — Compute reporting-day counts per market; rank the top reporter; count markets at 5 and 6 days.
Step 2.6 — Assemble the complete per-district fact sheet from Steps 2.1-2.5 and validate it by hand against the raw records for one district — a manual sanity check before any model ever touches this data.
Step 2.7 — Stand up Qwen3 (via vLLM; size chosen based on available GPU — 32B if a 24GB-class GPU is available, otherwise 7B/14B), IndicTrans2, and HHEM-2.1-Open. Write and unit-test the numeric diff-checker against the Step 2.6 fact sheet.
End of Day 2 exit criteria: complete fact sheets for ALL Madhya Pradesh districts, with hand-verification against raw records on a small spot-check sample of districts (not all — exhaustive manual verification of every district's fact sheet does not fit Day 2's budget, matching the sampled-review principle carried through to Day 4); all three open-source models running and responding to test prompts; numeric diff-checker passes its unit tests.
Day 3 — Generate, Translate, Gate
Step 3.1 — Write the grounded narration prompt: the fact sheet only, explicit 'use only these numbers' instruction, 2-3 hand-written example briefs as few-shot exemplars covering every Section 1 requirement so the model has seen the full shape expected.
Step 3.2 — Generate the English brief for every district with Qwen3, batched via vLLM (its whole purpose is efficient parallel inference across many prompts, which matters at ~50-55 districts rather than a handful); run the numeric diff-checker on every district; on any failure, regenerate once, then route straight to the Day 4 human-review queue if still failing — these auto-failed districts are prioritized INTO the sample, not left to chance.
Step 3.3 — Translate each passing English brief to Hindi via IndicTrans2 using the fixed agri-terminology glossary, across all districts.
Step 3.4 — Run HHEM-2.1-Open over both language versions for every district; low-scoring districts are also prioritized INTO Day 4's review sample, alongside anything that failed the numeric gate.
Step 3.5 — Spot-check a handful of drafts by hand against the full Section 1 checklist (not exhaustive at this stage — Day 4 is where systematic review happens) to catch any structural prompt issue early, before it repeats across every district.
End of Day 3 exit criteria: two documents per Madhya Pradesh district (English + Hindi) exist, have been through the numeric gate and HHEM scoring, and a review queue exists ranking districts by risk (gate failures and low HHEM scores first).
Day 4 — Sampled Human Review, Fix, Export, Close Out
Step 4.1 — Human review of a representative sample (15-20% of districts) PLUS every district that failed the numeric gate or scored low on HHEM in Day 3 — risk-based sampling, not pure random, so review time goes where it's most likely needed. Reviewer checks: every number against the fact sheet, Hindi naturalness, no unsupported claims the numeric gate wouldn't catch.
Step 4.2 — Fix anything the sample surfaces; re-run affected districts through the numeric gate. If the sample turns up a systemic issue (e.g. a prompt-structure problem affecting many districts, not just the sampled ones), fix it and re-run the numeric gate across ALL districts, not just the sample — a systemic fix earns full re-verification.
Step 4.3 — Export every district's approved briefs to HTML (bilingual toggle) and DOCX, matching the established template.
Step 4.4 — Write the close-out note: which data source ended up locked in (Section 2's outcome), confirmed field coverage, which districts were sampled and what the sample found, and — critically — an explicit statement that districts outside the sample shipped on the strength of the automated gate alone (see Section 8's residual-risk note on this).
End of Day 4 exit criteria: two documents per Madhya Pradesh district delivered as HTML + DOCX; every Section 1 requirement traceable to a working, demonstrated piece of the pipeline per Section 6; sampled districts reviewed and any systemic issues fixed state-wide.
8. Residual Risk
Risk 1 — Day 1 source stabilization. Whether Selenium-based scraping of agmarknet.gov.in stabilizes quickly enough within Day 1's budget, now at full state-wide volume rather than a handful of districts, which makes this risk larger than in the pilot-scope version of this plan. Day 1 is structured as a decision tree rather than a single assumed path — if the primary source is taking too long to stabilize, or state-wide volume is taking too long to complete, the plan falls through to the logged fallbacks in Section 2 rather than stalling.
Risk 2 — Sampled review means most districts are never seen by a human before publishing. This is the direct trade-off of covering all of Madhya Pradesh in 4 days rather than a small pilot. For the ~80-85% of districts outside the review sample, the ONLY accuracy safeguard is the automated gate: the numeric diff-checker (a hard, deterministic, byte-for-byte check — genuinely reliable) and HHEM-2.1-Open's grounding score (a secondary, weaker signal — publicly benchmarked at only 64-77% balanced accuracy at catching non-numeric issues, per the earlier design-plan evaluation notes). In plain terms: a wrong number in an unreviewed district's brief is very unlikely to slip through, because the numeric gate is exact-match and deterministic. A subtler issue — a mischaracterized trend, an awkward or misleading phrase in the Hindi translation — has a real, non-trivial chance of slipping through in an unreviewed district, because HHEM is the only thing checking for that class of error and it is known to miss roughly a quarter to a third of such issues. This is the honest cost of choosing full-state coverage over full review depth, and it should be stated to whoever signs off on the Day 4 output, not discovered later.
Risk 3 — Day 3's inference volume. Generating and gating ~100-110 documents (all districts x 2 languages) in a single day via self-hosted, non-batch-optimized-by-default open models is a meaningfully larger compute job than a 6-document pilot. vLLM's batching is what makes this realistic; if GPU capacity is thinner than expected, this is the step most likely to run long and compress Day 4's review window.
